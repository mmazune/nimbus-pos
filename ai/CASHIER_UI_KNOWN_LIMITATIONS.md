# Cashier UI Known Limitations

Date: 2026-07-02
Repo: `C:\Users\arman\Desktop\nimbus-pos`

These limitations are intentional boundaries or unresolved demo/runtime constraints observed during final cashier UI QA. They should be disclosed during demos and not described as completed live integrations.

| ID | Area | Limitation | User-visible copy | Severity | Demo impact | Owner | Status |
|---|---|---|---|---|---|---|---|
| CASHIER-LIM-001 | Mobile money | MTN MoMo and Airtel Money are reference/manual confirmation flows only. Live diner checkout is pending provider confirmation. | Payment method caveats warn that provider confirmation is pending before settlement. | High | Do not demo as live mobile money collection. | Payments/backend | Known limitation |
| CASHIER-LIM-002 | PesaPal | PesaPal diner checkout is intentionally excluded from cashier UI. | Cashier payment copy does not present PesaPal as a cashier collection method. | Medium | Do not promise cashier-side PesaPal checkout. | Payments/product | Intentional boundary |
| CASHIER-LIM-003 | Card payments | Card terminal/acquirer integration is not live; card references are manual/reference based. | Card method caveat identifies external terminal/acquirer requirements. | High | Demo as recorded external payment reference only. | Payments/hardware | Known limitation |
| CASHIER-LIM-004 | Receipt printing | Printer routes are metadata-only until a real printer driver/adapter exists. | Receipt UI warns that print output depends on pending printer integration. | Medium | Do not demo physical printing as complete. | Hardware/platform | Known limitation |
| CASHIER-LIM-005 | Receipt delivery | SMS/email receipt delivery adapters are pending. | Send receipt UI presents delivery as pending adapter work. | Medium | Do not claim real customer receipt delivery. | Notifications/platform | Known limitation |
| CASHIER-LIM-006 | Till movements | Paid in, paid out, and pickup flows are deferred. | Deferred cash movement card identifies these actions as not active in cashier UI. | Medium | Limit till demo to open, safe drop, reconcile, and active till visibility. | Cash management | Deferred |
| CASHIER-LIM-007 | Safe drop idempotency | The frontend sends an idempotency key, but backend safe-drop wrapping was previously documented as not fully BG3-complete. | No special customer-facing copy beyond normal safe-drop workflow. | Medium | Avoid using repeated safe-drop retries as a demo proof point. | Backend/cash management | Known limitation |
| CASHIER-LIM-008 | Split bill | Split bill remains allocation metadata and does not create child orders. | Split bill copy explains metadata-only allocation. | Medium | Demo as payment allocation support, not kitchen/order splitting. | POS/product | Intentional boundary |
| CASHIER-LIM-009 | Split items | Split items can create a `NEW` child order but does not send it to KDS. | Split item warning explains no KDS dispatch. | High | Do not imply kitchen receives split child orders. | POS/KDS | Intentional boundary |
| CASHIER-LIM-010 | Server transfer | Transfer server is a boundary-only/deferred cashier surface. | Transfer server panel is visibly deferred. | Low | Do not demo as active employee reassignment. | Workforce/POS | Deferred |
| CASHIER-LIM-011 | Partial cash tender | Partial cash tender is blocked until partial settlement support is explicit. | Payment validation blocks partial cash. | Medium | Demonstrate cash only as final full settlement. | POS/payments | Intentional boundary |
| CASHIER-LIM-012 | Refund approvals | Manager approval and post-close void are boundary cards only. | Refund UI shows approval/post-close void as restricted or future manager flows. | Medium | Demo refund request/listing, not manager approval execution. | Manager/POS | Deferred |
| CASHIER-LIM-013 | Bill-requested filter | Bill-requested queue state is derived from order/audit signals rather than a dedicated source document. | Queue helper copy explains inferred bill-requested status where applicable. | Low | Safe to demo with explanation if data supports it. | POS/backend | Known limitation |
| CASHIER-LIM-014 | API startup | API startup can be slow and quiet; direct `node dist/main` after `nest build` was needed for the authenticated QA pass. | Not product UI copy. | Medium | Demo operator should confirm `/api/health` before browser walkthrough. | Local environment/API | Documented |
| CASHIER-LIM-015 | Demo credentials doc drift | `demo-data/DEMO_LOGIN_CREDENTIALS.md` still contains older cashier route/limitation wording from before cashier routes existed. | Product UI points to the file but does not expose credentials. | Low | Demo operator should use the current walkthrough and route `/cashier/queue`. | Docs/demo | Needs cleanup |
