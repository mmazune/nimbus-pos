# Waiter MVP Known Limitations

| ID | Area | Limitation | Impact | Current Safe Behavior | Owner/Next Action | Status | Last Updated |
| -- | ---- | ---------- | ------ | --------------------- | ----------------- | ------ | ------------ |
| WKL-001 | Request bill | Backend `POST /api/pos/orders/:id/request-bill` currently accepts `NEW` orders, while waiter MVP policy requires orders to be sent first. | A direct API caller could request a bill earlier than the waiter UI allows. | Waiter UI blocks `NEW` orders with `Send order before requesting bill.` and does not expose payment collection. | Backend/product: tighten request-bill state contract when source documents are stable. | Safe UI block / backend gap | 2026-07-01 |
| WKL-002 | Me / employee linkage | The imported `waiter@nimbus.demo` account has a verified linked employee and can use permitted self-service actions; fallback accounts may still have no linked employee. | Unlinked accounts cannot safely read or submit employee-bound attendance, leave, or shift-swap data. | Linked accounts use `auth/me.employee.id`. Unlinked accounts issue no employee-dependent queries, show one capability notice, and use compact unavailable states without guessing or creating an employee. | Administration/data: link the user account to the correct employee when self-service is required. | Account-dependent safe boundary | 2026-07-18 |
| WKL-003 | Me / shift swaps | Shift swap creation remains read-only because no waiter-safe target employee selector exists. | Waiter cannot create swap requests from the MVP UI. | Self-scoped swap reads remain available; creation is not exposed. | Product/backend: define waiter-safe target selection before enabling create. | Safe read-only | 2026-07-01 |
| WKL-004 | Demo data | Local QA fixtures disappear after DB reset/import unless intentionally added to the demo import. | Demo tables/reservations created during QA may not survive a reset. | Demo script prefers named QA fixtures when present and falls back to any safe available/confirmed demo row. | Demo data: promote intentional QA fixtures into the import pack if they should persist. | Demo-data follow-up | 2026-07-01 |
| WKL-005 | Public diner payments | Public diner mobile-money remains pending/provider-gated for MTN/Airtel confirmation. | No live public diner mobile-money checkout should be demonstrated or implied. | Waiter UI does not add mobile-money checkout or payment collection. | Payments/product: wait for provider confirmation before exposing live diner flow. | CRITICAL - PENDING MTN/AIRTEL PROVIDER CONFIRMATION | 2026-07-01 |
| WKL-006 | Receipt send | Receipt send remains pending because no live email/SMS/WhatsApp adapter is connected. | Digital receipt delivery cannot be claimed as delivered. | UI and backend show pending/no-adapter copy; no delivered state is faked. | Messaging/product: add a live adapter and update receipt contract when ready. | PENDING - no live adapter | 2026-07-01 |
| WKL-007 | Printer routes | Printer routes remain metadata-only. | Reprint actions do not invoke a physical printer driver. | Reprint records metadata/audit only and says no driver was invoked. | Hardware wave: add real printer driver integration later. | Metadata only | 2026-07-01 |
| WKL-008 | Terminal pairing | Terminal pairing remains stub-only. | No card terminal/acquirer traffic exists in this waiter MVP. | Waiter UI does not expose card terminal actions or acquirer traffic. | Hardware/payments wave: replace stub when real terminal integration is approved. | STUB only | 2026-07-01 |
| WKL-009 | Quick PIN branch context | Local Quick PIN login uses the seeded Tapas Downtown branch context until terminal provisioning or a broader branch selector exists. | The local demo is smooth, but non-demo terminals still need a configured branch ID. | Login auto-fills Tapas Downtown for the demo and keeps an editable branch input for other local contexts. | Frontend/product: add terminal provisioning or a waiter-safe branch selector when multi-branch terminal UX is in scope. | Demo-safe default | 2026-07-01 |
| WKL-010 | Sent-order additions | The order contract has no per-line sent state or dedicated endpoint for dispatching additions after an order reaches `SENT`; calling the existing send endpoint again is an invalid `SENT -> SENT` transition and KDS ticket generation cannot safely identify only new lines. | The waiter cannot safely send later additions to kitchen/bar without risking undispatched items or duplicate KDS tickets. | Floor shows the active order and bill/receipt workflow, but keeps sent-order item mutations blocked with truthful copy. | Backend/product: add append-only line dispatch state or a dedicated idempotent send-additions contract with KDS coverage, audit, tests, and Postman. | Frontend-blocking backend gap | 2026-07-16 |
| WKL-011 | Demo taxonomy coverage | Tapas Downtown now has imported browse groups, subgroups, and item assignments for `GET /api/menu/navigation`; older QA notes that said Tapas navigation was empty are obsolete. | Agents using stale notes may misdiagnose a menu failure as expected empty configuration. | The UI treats loading, failure, true empty, and configured navigation separately; Tapas should show FOOD/DRINKS from the imported demo data. | Demo data/docs: keep taxonomy CSVs and importer in sync when menu fixtures change. | Resolved / monitor docs drift | 2026-07-18 |
| WKL-012 | Serving edits | `PATCH /api/pos/orders/:id/items/:itemId` accepts quantity, notes, and metadata, but not `menuItemServingId`. | A serving can be selected when adding an item but cannot be truthfully changed on an existing line. | The shared configurator displays the existing serving read-only in edit mode and explains the contract limit. | Backend/product: add a validated serving-change contract if operational rules allow it. | API contract limitation | 2026-07-16 |
| WKL-013 | Local authenticated QA latency | Prompt 4A removed the browser-pending deadlock and list request storms, but local Neon/API latency remains variable: warm Quick PIN reached ~3.8s after cold-ish ~9.9s, `/auth/me` reached ~1.46s warm, and menu item detail can still exceed 5s. | Automated browser QA can still miss aggressive timing targets under local cold starts even though role shells and mutations settle correctly. | Only one workspace API process should run on port 3001; item mutations clear after required backend confirmation while secondary refreshes run in the background; cashier/supervisor list screens no longer fan out per-row payment reads. | Backend/platform: add aggregate list summaries or local/pool tuning if strict warm targets must be met in this environment. | Residual external/backend latency | 2026-07-18 |
